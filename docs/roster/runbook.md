# 運用手順（部員名簿の反映）

担当者の画面は kintone管理サイト「部員名簿（Forms 提出）」。承認の正本はここだけで、Forms 管理画面の一覧は表示のみ。

## 日常の流れ

1. 「名簿の提出・承認」で「確認待ち」を開く。
2. 提出詳細で、kintone の現在の名簿との差分（追加・変更・状態変更・学籍番号の訂正・提出に含まれない既存行）を確認する。
   - 赤字の項目は、団体が名簿を読み込んだ後に kintone 側で変更された項目。accept すると提出内容で上書きされる。
   - 「学籍番号の訂正」は既存行の学籍番号が変わるもの。別人との入れ替えでないか確認する。
3. 問題があれば理由を書いて「差し戻す」。団体の画面に「第N版への差し戻し理由」として表示される。
4. 問題なければ「accept して反映を予約」。次回の定期実行（5分ごと）で反映される。急ぐときは「定期実行を待たずに今すぐ処理」（定期実行と同じ処理・確認を通る）。

## 反映状態ごとの対応

| 状態 | 意味 | 対応 |
| --- | --- | --- |
| 反映待ち | accept 済み・未実行 | 待つ（または今すぐ処理）。取り消すと提出は確認中に戻る |
| 反映中 | ワーカーが処理中 | 待つ。10分以上続く場合はワーカーの停止を疑う（自動で復旧する） |
| 反映済み | kintone へ書き込み、読み戻して内容を確認済み | なし |
| 反映失敗 | 未適用と判断できるエラー | 失敗理由を確認し、原因を解消してから「再試行」 |
| 競合・要確認 | kintone 側の変更、同じ団体のレコードが複数など | 下記「競合のとき」 |
| 結果確認待ち | 書込みの成否が不明（通信断など） | 自動で照合する。急ぐときは「次回の実行ですぐに照合する」→「今すぐ処理」 |

### 失敗の種類

| 種類 | 例 | 自動再試行 | 対応 |
| --- | --- | --- | --- |
| 一時的な通信障害 | 接続失敗、429、取得時の 5xx | する（1分→5分→15分…、最大6回） | 続く場合は kintone の稼働状況を確認して再試行 |
| 設定エラー | フィールド不足・選択肢の不一致、トークン未登録 | しない | 「反映・接続の確認」で不足を確認し、kintone のフィールドを追加・修正してから再試行。accept 済みの内容は保持されている |
| 権限エラー | トークンの権限不足、ルックアップ参照先（ID7）のトークン不足 | しない | トークンの権限を見直して再登録し、再試行 |
| 入力値・フィールド設定エラー | CB_VA01（必須・選択肢）、ルックアップの失敗 | しない | エラーの項目を確認。必須設定や選択肢を直すか、差し戻して団体に修正してもらう |
| 反映後の照合不一致 | 書き込んだ内容を読み戻したら一致しない | しない | kintone のレコードを直接確認し、取り消して accept し直す |

### 競合のとき

- **accept 後に kintone で名簿が更新された**（リビジョンが変わった）: 上書きせずに停止している。「accept を取り消す」→ 差分を見直して改めて accept する（必要なら差し戻して団体に読み込み直してもらう）。
- **同じ団体のレコードが複数ある**: 最初の1件を選ばずに停止している。kintone 側で1件に整理（不要なレコードの統合・削除は担当者が判断）してから、取り消し → accept。
- **accept 後に同じ団体のレコードが作られた／消えた**: kintone 側の経緯を確認してから、取り消し → accept。
- **学籍番号が一致する既存行が複数ある**: kintone 側で重複行を整理してから accept する。

### 結果確認待ちのとき

- 新規登録（POST）の応答が届かなかった場合、同じ登録を繰り返さず、5分以上おいて ID20 を検索する。
  - レコードがあり内容が承認内容と一致 → 反映済みにする（再登録しない）。
  - レコードがない → 未登録と確認できたので1回だけ登録する。
  - 内容が一致しない・複数ある → 競合にして担当者の確認を待つ。
- 更新（PUT）の応答が届かなかった場合、リビジョンが変わっていなければ未適用として同じ期待リビジョンで再送し、変わっていれば内容を照合する。
- 結果確認待ち・反映中の間は、団体は新しい提出ができない（入力内容は下書きとして保存される）。古い内容と新しい内容の反映順が入れ替わらないようにするため。

## 年度の切り替え

1. Forms 管理画面で名簿フォームの対象年度を変更する（または新年度用のフォームを作る）。
2. 前年度の未反映の accept は、実行時に「過年度」として失効する（現行名簿へ反映されない）。
3. kintone ID20 は団体ごとに1件の現行名簿として扱い、年度別の履歴は XServer の提出原本・accept・反映履歴に残る。

## ワーカーの確認と手動実行

```
php apps/jobs/roster_kintone_apply.php                # 通常の実行（cron と同じ）
php apps/jobs/roster_kintone_apply.php --job=123      # 指定ジョブだけ（accept の有効性確認は同じ）
php apps/jobs/roster_kintone_apply.php --refresh-groups
```

- 出力は1行の JSON（処理したジョブと結果）。cron のログは `apps/kintone_core/storage/roster_worker_cron.log`、詳細は `apps/kintone_core/storage/kintone_manager.log`（`[roster]` 行。部員の個人情報は書かない）。
- ワーカーが書込み送信後に止まった場合、期限付きロック（10分）が切れた後に「結果確認待ち」になり、照合してから再処理する。送信前に止まった場合は反映待ちに戻る。

## 個人情報の扱い

- 下書きはサーバー（fitsc_forms）に保存し、ブラウザの localStorage は使わない。
- 反映の試行記録・ログには、件数・エラーコード・項目名だけを残し、部員の氏名・電話番号は残さない。
- 確認コードはハッシュで保存し、30日を過ぎた確認記録はワーカーが削除する。
- 提出原本（リビジョン）は業務記録として自動削除しない。保持期間を決めた場合は別途削除処理を追加する。
