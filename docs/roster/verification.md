# 検証結果（2026-11-08）

実レコードは使わず、kintone はメモリ上の模擬（`tests/support/fake_kintone.php`）で置き換えた。
模擬は kintone の仕様どおり「送らなかった行は削除」「存在しないフィールドは無視」「リビジョン不一致は 409 GAIA_CO02」
「ルックアップ参照先のトークンがなければ拒否」とし、仕様に明記のない「行IDを指定して一部の項目を省いた場合」は
項目が空になる厳しい側で再現した（実装は常に全項目を送るため、どちらでも既存値を保持する）。

## 環境

- DB: MariaDB 10.5.22（Docker、使い捨てコンテナ）に `localhost.sql`（2026-11-08 の構造ダンプ）を取り込み。本番は 10.11。`SKIP LOCKED` は使っていない
- PHP: 8.5.7（CLI・組み込みサーバー）。本番要件は PHP 8.1 以上（`never` 型・`array_is_list` を使用）
- 画面: PHP 組み込みサーバー＋アプリ内ブラウザで、Forms（団体側・管理画面）と kintone管理サイトを操作して確認

## 実際の kintone での確認（2026-11-08・試作スペースのテスト用アプリ）

本番の ID20 は使わず、試作スペースに ID20 を再利用したテスト用アプリ（アプリID 184「部員名簿（連携テスト）」）を作って確認した。
テーブルに `membership_status`・`uses_group_email`・`is_website_editor` を追加（必須なし・初期値なし）し、
引き継がれた通知（学生課など実在の組織あて）はテスト用アプリだけオフにした。
APIトークンは、アプリ184（閲覧・追加・編集）と本番 ID7（閲覧のみ。ID7 は公開中と編集中の設定が一致していることを確認してから更新）を担当者が発行し、ローカルの kintone管理サイトに登録した。

`tests/support/roster_live_check.php --confirm-app-id=184 --group=CA056` の結果（部員は架空のテストデータ）:

| 確認 | 結果 |
| --- | --- |
| フィールド確認 | 必要なフィールド・選択肢がそろっていると判定（ルックアップの詳細は参照先の権限がないトークンでは `lookup: null` で返るため、その場合も警告しないよう修正） |
| ID7 からの団体一覧 | 68団体を取得、提出対象（格・活動状況で絞り込み）60団体。確認コードの宛先（団体メール）を取得 |
| 初回の accept → 反映 | API トークン（ID20 用＋ID7 用）で**新規登録できた**。ルックアップの絞り込み条件（`PRIMARY_ORGANIZATION()`）で弾かれず、団体名がコピーされた。状態・チェックボックス・役職（部長・主将→代表者）も正しく保存 |
| kintone から読込→変更→再提出→accept→反映 | 同じレコードを更新（リビジョン 1→2）、既存の行ID 3/3 を維持、状態（入部→退部）・役職（会計長→副代表者）の変更と追加行を反映 |
| accept 後に kintone を直接編集 | 反映は「競合」で停止し、直接編集した値（職名）は上書きされなかった。取り消しでジョブ失効 |

テスト用アプリ184には、このテストのレコード（CA056・架空の部員4名）が残っている。不要になったらアプリごと削除してよい。

ローカルの Windows 版 PHP には CA 証明書の設定がなかったため、確認時は `-d curl.cainfo=…`（Git for Windows 同梱の ca-bundle.crt）を指定した。XServer では不要。
