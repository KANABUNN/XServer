| PR | 範囲 |
| --- | --- |
| [#6](https://github.com/KANABUNN/XServer/pull/6)（マージ済み） | 役員入力・提出原本の版管理・ID22/ID21 の比較プレビュー（書込みなし） |
| このPR | 計画の accept と固定、団体単位の書込み予約、ワーカーのステップ実行（ID20 → ID22 → ID21）、読戻し・照合・再開、代表者の履歴 |

**既定では ID22・ID21 へ書き込まない。** 書き込むのは、サーバー設定 `roster.officers.write_enabled` が `true` で、admin が「反映・接続の確認」で指定した団体・フォーム・年度の accept だけ。それ以外の accept は第1段階と同じく ID20 だけを反映する。

## 入力と比較（PR #6）

## 書込みの仕組み（このPR）

### accept で固定するもの

書込み対象の accept では、反映計画を作り直して担当者が見た計画の指紋と照合し、一致したときだけ承認スナップショット（版2）に固定する。承認原本・ジョブ・ステップの初期行は同じトランザクションで作る。

| 固定する内容 | 使い道 |
| --- | --- |
| 案件・フォーム・年度・提出ID・原本ハッシュ | すり替え・過年度の反映を検出する |
| ID20 の部員行 | 第1段階と同じ名簿の反映 |
| ID7 の団体レコードID | 団体の削除・差し替えを検出する |
| 人物ごとの操作（参照／新規）・比較元のレコードID・承認した申告 | 新規登録と既存参照の判断を固定する |
| ID21 の比較元のレコードID・リビジョン・各枠の操作・登録日 | 確認した役員構成を再現する。登録日は `accepted_at` と同じ時点の日本日付 |
| 接続先テナント・4アプリのアプリID・書込み対象の設定の世代 | 承認後に接続先や対象を変えたら止める |

スナップショットのハッシュは計画全体を決まった順序で計算する（第1段階の版1は従来どおり部員行のハッシュ）。

### ステップの実行

ワーカーは cron・CLI・「今すぐ処理」・再試行のすべてで同じ処理を通る。

1. **確認**：accept の有効性、スナップショットのハッシュ、接続先・アプリID・書込み対象の設定の世代を確認する。変わっていれば新しい書込みはしない（結果確認待ちの照合だけは行う）。
2. **ID20**（`roster`）：第1段階と同じ反映と読戻し。確認できた時点で ID20 の最終反映版を更新する（役員の反映とは別に記録する）。
3. **ID22**（`person_N`）：既存参照は、レコードID・区分・氏名が accept 時と同じかを確認する（書き込まない）。新規登録は学籍番号・メールで照合してから1件だけ追加し、読み戻す。一意制約に当たったら学籍番号で照合し直し、申告どおりの人物だけを参照する。
4. **ID21**（`ledger`）：ID7 と ID22（ルックアップ元）、ID21 の比較元を直前に確認し、レコードIDと期待リビジョンで更新する（新規は団体キー付きで追加）。送るのは変更する枠・コピーの取り直しが必要な枠・変更時の登録日だけ。読戻しで、団体キー・登録日・各枠の学籍番号・ID22 の現在値からコピーされた氏名とメール・空席の3項目を確認する。
5. 全ステップを確認できたらジョブを「反映済み」にする。

各ステップは「待機 → 送信前記録 → 読戻し → 確認済み」。送信後に成否が分からなければ、そのステップを「結果確認待ち」にして、次回は一意な値（学籍番号・メール・団体キー）と期待リビジョンで照合する。照合で反映済みと確認できたら書込みを繰り返さない。

### 団体単位の書込み予約

`roster_group_apply_guards` を団体ごとに1行持ち、処理中のジョブIDと、役員の書込みを認めるフォーム・年度・設定の世代を記録する。

- ロック順は「団体の予約 → 案件 → ジョブ → ステップ」で、accept・実行・復旧・完了で統一した。
- 同じ団体の別フォーム・年度に未完了の反映（待機・実行中・結果確認待ち）があれば accept しない。
- 結果確認待ちの間は予約を保持し、同じ団体の他のジョブを実行しない。

### 代表者の履歴

`roster_officer_history`（ID21 から独立）に記録する。表示は第3段階の団体管理UIで扱う。

- 基準：初回の上書き前の現任代表者（新設団体は初回登録した代表者）。団体ごとに一度だけ。
- 交代：ID21 の読戻しで交代を確認したときに、前任・後任の学籍番号と当時の氏名、反映日時、accept・ジョブ・台帳レコードの参照先を、ステップの確定と同じトランザクションで記録する。キーは accept ごとに固定なので、中断・再開しても一度だけになる。就任日は不明なので空欄。
- 学籍番号が変わらない再提出や氏名・メールの訂正は交代に数えない。
- 管理者が手動で処理した交代の記録画面は、団体管理UIで追加する（このPRには含まない）。

## 導入手順

1. **DB**：`apps/roster_core/migrations/002_roster_officer_sync.sql` を fitsc_forms に実行する（3テーブルの追加と `roster_apply_attempts` への列追加。再実行できる）。生成は `php tools/roster_migration_sql.php 002`、一致の確認は `--check`。
2. **トークン**：「アプリ設定」の `roster_people`（ID22）と `roster_officers`（ID21）を、書込みに必要な権限のトークンに替える。

   | app_key | 権限 |
   | --- | --- |
   | `roster_people`（ID22） | レコード閲覧・追加 |
   | `roster_officers`（ID21） | レコード閲覧・追加・編集 |

   ID21 へ書くときは ID7・ID22 のトークンも一緒に送る（ルックアップ元）。
3. **ID21 の移行**（試作アプリで手順を確認してから本番で行う）
   - 既存レコードを全件照合し、団体ごとに現行1件に整理する。
   - 文字列（1行）`forms_current_group_key` を追加し、既存レコードに団体識別記号を補完してから、必須・値の重複禁止にする。
   - 総務1（`general_affairs_1_stundet_id`・`_name`・`_mail`）の必須を解除する。
   - 副代表者1の欠落を確認して補ったうえで、副代表者1（ルックアップとコピー先）を必須にする。
   - 「反映・接続の確認」の「いま確認する」で、「書込みを有効にする前に必要な設定」が出なくなることを確認する。
4. **サーバー設定**：`apps/config.php` の `roster.officers.write_enabled` を `true` にする。`clear_enabled` は、空席の解除を試作アプリで確認するまで `false` のまま（`false` の間は、解除を含む計画を accept できない。台帳で手動解除してから比較し直す）。
5. **対象の指定**：「反映・接続の確認」の「第2段階：役員の書込み対象」で、admin が団体とフォーム（年度）を指定する。指定前に同じ団体の未完了の第1段階ジョブを解消しておく。指定を変更すると設定の世代が進み、変更前の accept は実行時に止まる。

## 運用

| 状況 | 対応 |
| --- | --- |
| 比較に「解消が必要な項目」 | 差し戻す、または kintone 側（ID22 の訂正・ID21 の整理）を直してから比較し直す。役員を含む accept はできない |
| 部員名簿は反映済み・役員は停止 | 反映状況のステップ表で止まった反映先を確認する。設定・一時障害なら原因を解消して「再試行」（失敗したステップから再開）。競合なら kintone を確認してから accept を取り消し、最新の差分で accept し直す（ID20 は変更なしとして照合される） |
| 結果確認待ち | 次回の実行で照合する。同じ追加・更新は繰り返さない |
| ID22 だけを訂正した | 次の accept で、ID21 の該当枠のルックアップを取り直してコピーを最新にする |
| 書込みを止めたい | `write_enabled` を `false` にするか、対象から外す。処理待ちのジョブは新しい書込みをせずに止まり、確認済みのステップはそのまま残る |

ステップ・試行の記録には学籍番号・氏名・メールを残さない（人物は `person_N` で示す）。人物の申告は承認原本（`roster_acceptances.snapshot_json`）だけにあり、詳細な属性は operator 以上にだけ表示する。

### 未検証（試作アプリで確認すること）

模擬 kintone は実機の仕様を厳しい側で再現しているが、次は実機でしか判定できない。確認するまで本番の書込みは有効にしない。

- ルックアップを含む ID21 への書込みに必要なトークンの組合せ（ID21・ID7・ID22）
- ルックアップの学籍番号を空にしたとき、コピー先の氏名・メールも空になるか（`clear_enabled` の前提）
- API で同じ学籍番号を送り直したときに、ルックアップのコピーが最新値で取り直されるか
- `forms_current_group_key` の必須・重複禁止と、既存レコードへの補完
- 一意制約に当たったときのエラー（`CB_VA01` と「重複」を含むメッセージ）の形
- ID22 の選択肢（`depend`・`type`・`org_depend_state`）と計算フィールド `name` の結果
- 実行時の通知（試作アプリでは通知を止めて確認する）
